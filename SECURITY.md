# Security

## Reporting a vulnerability

Please report vulnerabilities privately by opening a security advisory on the repository:
<https://github.com/robeertm/lanloom/security/advisories/new>

Do not open a public issue for security problems. Include the version, a description, and steps to reproduce if you can. Reports are handled on a best-effort basis.

## Security model

- **Sign-in is mandatory.** There is no open mode. The first account can only be created with the one-time setup code printed to the log and written to `setup-code.txt` in the data volume.
- **Passwords** are at least 10 characters and hashed with argon2id. Passkeys (WebAuthn) are available in secure contexts (HTTPS or localhost).
- **Sessions** are random 256-bit tokens in an `HttpOnly`, `SameSite=Strict` cookie (`Secure` on HTTPS). They last 30 days and expire after 14 days of inactivity. Users can list and end their own sessions; admins can end any user's.
- **Login rate limit:** after 5 failed sign-ins from the same client address, that address has to wait, starting at 60 seconds and doubling up to 1 hour. IPv6 addresses are counted per /64. Behind a reverse proxy, list it in `LANLOOM_TRUSTED_PROXIES` so the limit counts the real client: `X-Forwarded-For`, `X-Real-IP` and `X-Forwarded-Proto` are believed only from those addresses, and `X-Forwarded-For` is read from the right. The limiter's memory is bounded without forgetting active lock-outs.
- **Roles are enforced on the server.** Every route needs one of three roles (viewer, operator, admin) according to one central table (`lanloom/access.py`). A test checks every route of the app against the table, and a route that is missing from it is for admins only. The web page only hides controls. Location fields of the site are redacted for everybody but admins.
- **Second factor.** Authenticator app (TOTP, 6 digits, 30 seconds, each code usable once) with 10 recovery codes stored only as keyed hashes, or a passkey. Required for admins by default, adjustable per role with a grace period. The second step uses a ticket that expires after 5 minutes and allows 5 tries, and is rate limited per client and per account.
- **Step-up confirmation.** Critical actions (users, connections, sign-in security, AI pairing, own passkeys and factors) need a confirmation within the last 10 minutes by passkey, app code or recovery code. Executor approvals stay passkey-signed every time.
- **Invitation and reset tokens** are random, stored only as hashes, valid for 24 hours and usable once. An invitation is bound to its role. Using a reset link ends all sessions of that user. Sessions of a public or shared computer end with the browser, after 8 hours or after 30 minutes without use.
- **Audit log.** Every state-changing action is recorded with user, role, time, target, result and origin; secret values are never written. Entries form a hash chain (HMAC-SHA-256 keyed from `secret.key`) and the newest hash is kept separately, so edits, insertions and cut-off ends are shown. This is tamper-evident, not tamper-proof: someone with the database, `secret.key` and write access could rewrite it consistently. Details: [docs/ACCESS.md](docs/ACCESS.md).
- **Trusted-header sign-in is off by default.** When enabled (`LANLOOM_AUTH_HEADER`), the user and group headers are believed only if the direct peer is listed in `LANLOOM_TRUSTED_PROXIES`; the proxy must strip them from client requests. A second factor is not asked in that case, the proxy is responsible.
- **Cross-site protection:** state-changing requests need the header `X-Lanloom: 1` and a matching `Origin`. Behind a reverse proxy, list the public origin in `LANLOOM_TRUSTED_ORIGINS`.
- **Strict Content Security Policy** on the web interface.
- **Firewall editor:** the app never writes to a network device. By default the editor is a simulation. Real changes run only in the optional executor container, which verifies a passkey signature (user verification required) over the SHA-256 of every plan against keys pinned by the operator, applies its own gate (at most 10 objects, lockout protection, fresh state, nonce, expiry), backs up before writing, watches afterwards and rolls back on its own. Real writes need a built-in adapter, the phrase `LANLOOM_EXECUTOR_ARM=I-UNDERSTAND` and a file created by hand; the executor routes of the app need a shared token. Every plan step must be covered by the adapter's capability list; firmware, restarts, accounts, keys, remote access, VPN and WAN settings, port mirroring and factory resets are no step kind at all.
- **Adapters are built in only.** There is no mechanism to load code from elsewhere (no plugin folder, no module path from the environment). Each adapter has a read half (web app, read-only account, one send path that only allows reads) and a write half (executor only, its own credentials). The web app never imports a write half; static tests check both.
- **Credentials are kept apart.** Read-only accounts live encrypted in the app; an account that reports it can write is refused where that is checkable. Write credentials live only in the executor's options file (mode 0600, owned by the executor's user, never through a symbolic link); superuser principals are refused, an account that cannot write is refused, owner-level roles give a warning. A write half can bind its connection to the device's certificate (SHA-256 pin).
- **Connection guard in the executor.** The executor process can connect only to the app and to the addresses of its controller (resolved at start); every other connection is refused before it is made. `LANLOOM_EXECUTOR_DENY_HOSTS` lists addresses that are refused even then (a rehearsal executor against a test controller lists the real one).
- **Write halves check what controllers do not.** Before writing, the gate and the write half check addresses (inside the network, not the gateway, not used by another device, not twice in one plan) and that a network exists and is local; after writing they read the object back and roll back when the value did not take. Sign-ins of a write half are capped across restarts (four an hour, 15-minute pause after a refused session; one new sign-in after 401, none after 403).
- **Use at your own risk.** Changes on a controller can interrupt connections. Keep local console access; Lanloom never writes without your passkey. This is no legal advice and no warranty.
- **Container hardening:** runs as an unprivileged user (uid 10001) with a read-only root file system, all capabilities dropped and `no-new-privileges`.
- **Read-only by construction.** The scanner only sends the probes described in the README, never targets public ranges and never attempts logins. Integrations use strict allow-lists: the hub connection can only authenticate, read states, configuration and registries, and subscribe to state-change events; the MQTT client can only connect, subscribe, ping and disconnect; SNMP uses Get, GetNext and GetBulk only; the switch controller connection can only sign in (and out) and read the client and device lists, through one request path that refuses everything else.
- **Credentials** for integrations are encrypted with AES-256-GCM using a key file (`secret.key`, mode 0600) in the data volume. They are never shown again and never logged. Anyone with access to the data volume can read both the key and the encrypted values, so protect the host and its backups.
- **Backups are encrypted with your passphrase.** Settings › Backup writes one file: Argon2id (64 MiB, 3 passes) derives a key from the passphrase, a random data key per file encrypts the content with AES-256-GCM, and the header is authenticated with it, so a changed file is refused. Credentials are inside the encrypted content only; the instance key `secret.key` is never part of a backup, and a restored instance encrypts every credential again with its own key. The passphrase is never stored (automatic backups keep only the derived key, encrypted with the instance key), never logged and never written to the audit log. Export, file download, restore and the automatic-backup settings are for admins with a fresh confirmation; a restore ends every session and is written to the audit log, and an instance that has its own audit log keeps it. Restoring before the first account exists needs the one-time setup code and is rate limited, like wrong passphrases. See [docs/BACKUP.md](docs/BACKUP.md).
- **No telemetry.** The only outbound connection of its own is the optional update check against the public release feed (`api.github.com`), at most every 6 hours (15 minutes after a failed check) and only while the page is open. Turn it off with `LANLOOM_UPDATE_CHECK=0` or in the settings. Everything else is opt-in: report delivery and notifications (below), the optional heartbeat to an address you enter, and AI. A cloud AI service is contacted only after you set it up and switch it on, only for the functions you allow, and only with placeholders instead of addresses, names and serial numbers; a local AI service gets the real text but stays in your network. The local AI service image and the models are downloaded only when you click for them.
- **Nightly report delivery is opt-in.** The nightly report is made on the host. Only when you switch on a delivery channel (e-mail, webhook, push topic, chat bot) does Lanloom send a short summary (title, headline, two lines, optional link) to the address you entered, once a morning, with up to three quiet retries. Device ids and other internal values are never sent. Passwords, tokens, the webhook address and the push topic are encrypted like other credentials and never logged; failures are reported as reason codes without the address. To read certificate expiry dates for the report, Lanloom opens one TLS handshake per morning to the addresses of your own connections, nothing else.
- **Notifications are opt-in.** Every event goes into the nightly report unless a person chooses more for themselves. Messages go only through the channels of the report delivery or by web push to the push service of a browser the person subscribed; push messages are encrypted for that browser (RFC 8291) and signed with this instance's VAPID key (RFC 8292), whose private key and the push endpoints live in the encrypted secret store. Only subscription addresses at a named HTTPS host are accepted (no address literals, no `localhost`, no `.local`). Messages carry names and short texts, never device ids, passwords or tokens.
- **Heartbeat is opt-in.** When an administrator enters an address and switches it on, Lanloom sends a plain `GET` to it every 1 to 60 minutes and nothing else; the address is stored encrypted and never shown or logged.
- **Service worker.** The web app installs a service worker for push and an offline shell, only on the notifications page, in the installed app or once push is allowed. It asks the network first, caches only the page and its static files, and never caches the API.

- **AI is read-only and keyed.** AI only explains and never writes configuration. Keys are encrypted like other credentials and never appear in answers, logs, exports or reports. A final check refuses to send when an address pattern survived the placeholders, a daily limit caps cloud requests, and a local address that leads to the internet counts as a cloud service. See [docs/integrations/ai.md](docs/integrations/ai.md).
- **Pairing endpoints work without a session.** To pair another computer with the local AI setup, a script calls a few endpoints without signing in. They need the one-time setup code (valid 4 hours, stored only as a hash, used up after a successful pairing), are rate limited and accept only private peer addresses.

## Things to be aware of

- Host networking means the container shares the host's network stack.
- The optional updater sidecar mounts the container-runtime socket, which is root-equivalent on the host. Leave it out if you do not want that.
- Only scan networks you own or are allowed to scan. The deep scan may trigger security alerts.
- Lanloom serves plain HTTP. For remote access or passkeys, put it behind a TLS reverse proxy. Never expose it directly to the internet.
- Classifications and measurements are observations, not guarantees.
